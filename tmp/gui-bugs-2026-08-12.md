## Bug #1（已修复）：新会话首条消息发送后，主区域不进入会话视图

**严重度**：高（P0 主流程交互缺陷）

**现象**：
1. 在「新对话」欢迎页发送首条消息（粘贴简历）后，输入框清空、消息进入流式处理（服务端日志可见工具调用），但主区域始终停留在「新对话」欢迎页——用户消息与助手回复均不渲染；
2. 必须手动点击左侧「会话」列表中的新会话卡片，消息才显示；
3. 刷新/重开页面后，主区域一律回到「新对话」欢迎页，不会恢复最近会话（需要再次手动点击）。

**复现步骤**：
1. 打开 http://localhost:3000/（无活跃会话时）
2. 输入任意文本并点击发送
3. 观察：主区域仍是「新对话」欢迎页；左侧列表出现新会话卡片（含已完成的回复摘要）
4. 点击左侧会话卡片，消息才可见

**根因**（源码定位）：
- `src/components/chat/chat-panel.tsx`：`useChat({ id: internalConvId ?? undefined, ... })`；收到服务端 `data-conversation-id` 事件后 `setInternalConvId(id)`，useChat 的 `id` prop 从 `undefined` 变为真实会话 id。
- `@ai-sdk/react` 内部 `shouldRecreateChat` 判断：`"id" in options && options.id != null && chatRef.current.id !== options.id` 成立时执行 `new Chat(...)` **重建 Chat 对象，messages 被清空** → 首轮回复（含进行中的流式内容）在 UI 上丢失，EmptyState 欢迎页重新出现。
- `app/page.tsx`：`activeId` 仅存内存（`useState`），无任何持久化 → 刷新后必然回到「新对话」。

**修复**：
1. `chat-panel.tsx`：useChat 的 `id` 仅在挂载时确定（`useRef` 固化）；真实 conversationId 用 ref 追踪，仅用于请求 `body.conversationId`，不再回写 useChat id。
2. `app/page.tsx`：`activeId` 持久化到 localStorage（key: `job-helper.last-conversation-id`），挂载时恢复并加载消息；新建/删除会话时同步更新。

**验证**：
- 首条消息发送后，主区域立即渲染用户消息与流式回复（无需手动点击会话）
- 刷新页面后自动恢复最近会话视图

**验证结果（2026-08-12 实测）**：
- 场景 A：新会话发送「你好，我是新会话测试消息」→ 用户消息立即渲染，助手回复完整显示，标题自动更新 ✓
- 场景 B：刷新页面 → 自动恢复该会话视图（消息完整）✓
- 修复涉及文件：`src/components/chat/chat-panel.tsx`、`app/page.tsx`；tsc / eslint 通过

## Bug #2（已修复）：webFetch 网络异常冒泡为 TOOL_FAILED，误导性文案 + 降级链中断

**严重度**：中（错误提示误导用户 + 降级链语义破坏）

**现象**：抓取不可达/拒绝连接的站点（如 BOSS 反爬、目标域名不可达）时，失败步骤卡片显示「工具执行遇到未知异常。请稍后重试；若持续失败，请检查系统配置或联系维护者」——实际是目标站点网络不可达，用户被误导为本地系统配置问题。

**根因**（源码定位）：
- `src/agent/web-fetch-router.ts`：`directFetch` / `jinaFetch` 内 `fetch` 抛异常（TypeError: fetch failed / AbortError 超时）未捕获，直接冒泡：
  1. 冒泡到工具工厂被 TOOL_FAILED 兜底（hint 文案误导"检查系统配置"）
  2. **降级链被中断**：direct 抛异常不会继续尝试 jina/opencli（本应降级）
- `FETCH_FAILED` 错误码在类型中预留但从未实现（设计遗漏）

**修复**：
- `web-fetch-router.ts`：direct/jina/opencli 各层 fetch 包 try/catch，网络异常映射为结构化 `FETCH_FAILED`（message 含层名 + 原因，AbortError 映射为「请求超时」）；全链失败时按失败类型归码（全网络失败 → FETCH_FAILED，含站点拦截 → FETCH_BLOCKED）
- `web-fetch.ts`：routeFetch 调用兜底 catch（防御未知异常 → FETCH_FAILED，不再落入 TOOL_FAILED）

**验证**：
- 单测新增 4 用例（网络异常降级 jina / 全链 FETCH_FAILED / 混合原因 FETCH_BLOCKED / 超时映射），全绿
- 服务端实测 `webFetchTool.execute` 对不可达 URL：返回 `FETCH_FAILED`，message「抓取失败：direct（直接抓取网络请求失败（fetch failed））→ jina（Jina 渲染网络请求失败（fetch failed））」，hint 建议人工查看粘贴导入
- 全量 312 测试通过；tsc / eslint 通过

## 观察项（非缺陷，记录备查）

1. **webFetch 失败展示兜底文案**：「工具执行遇到未知异常。请稍后重试…」为 TOOL_FAILED 通用兜底（fetch failed 为平台反爬/网络原因）。展示层未区分错误码，属设计取舍，非缺陷。
2. **失败卡片「重试」按钮**：Agent 生成期间统一置灰、生成结束后恢复（与已知限制「重试按钮点击后置灰至重跑结束」一致，全局禁用是合理设计）。
3. **长对话页面 DOM 性能**：多轮长回复（简历全文 + 大表格）后页面 DOM 较大，IAB 工具操作（domSnapshot/click）多次超时；消息列表未做虚拟化。对话型应用常见做法，未达修复门槛，待真实长会话体验确认。
4. **「上传简历」按钮**：IAB 运行时不支持 file chooser（`capability_unsupported`），未验证上传路径；应用文案已提供「对话中粘贴文本导入」替代路径（本次测试走该路径）。
5. **AI SDK 警告**（非本应用缺陷）：`responseFormat` 特性不支持（deepseek-v4-flash 无 structuredOutputs），与 PROJECT_STATUS 已知限制一致。
