# 11 Context Engineering 与上下文管理

## 调研对象（链接 + 一句话）
- **Anthropic《Effective context engineering for AI agents》**（https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents）：2024 起的 context engineering 奠基文，提出"context rot"、最小高信号 token 集、compaction / agentic memory / sub-agent 三大长任务技术。
- **《Lost in the Middle》论文**（arXiv:2307.03172）：长上下文位置偏差研究——模型对首尾信息利用最好、中间最差（U 形曲线），是"关键信息放哪"的第一依据。
- **Anthropic Prompt Caching 官方文档**（https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching）：cache_control 机制、5m/1h TTL、读 0.1x / 写 1.25x-2x 定价、最小可缓存长度。
- **OpenAI Prompt Caching 官方文档**（https://platform.openai.com/docs/guides/prompt-caching）：gpt-4o 起自动缓存 ≥1024 token 前缀，前缀哈希路由、静态在前动态在后。
- **Claude Code Best Practices**（https://code.claude.com/docs/en/best-practices）：CLAUDE.md 渐进披露、agentic memory、子 agent 隔离上下文、自动 compaction，工程化落地参考。
- **Anthropic Context Windows 文档**（https://platform.claude.com/docs/en/docs/build-with-claude/context-windows）：1M 窗口默认可用、token 预算（context awareness）、server-side compaction。

## 核心原则（提示结构/位置偏差/分层注入）
1. **上下文是有限资源，存在 context rot**：LLM 召回质量随 token 数增长而下降。每轮注入"当前决策所需的最小高信号 token 集"，而非越多越好。
2. **关键信息放开头与结尾**：Lost in the Middle 证明首尾利用最好、中段最差；长上下文 + 大文档场景，重要内容（指令、待回答的核心材料）放前后，别埋中间。
3. **提示结构化分节**：system prompt 用 XML 标签 / Markdown 标题分成「背景 / 指令 / 工具说明 / 输出规范」；写在"正确高度"——既非硬编码脆弱逻辑，也非空泛口号；从最小化提示开始迭代，哪里出问题补哪里。
4. **分层注入（progressive disclosure）**：常驻高价值核心（system prompt / CLAUDE.md）＋ 按需动态加载（工具读文件、检索、子 agent）＋ 用完即清（tool result clearing 是安全轻量的压缩手段）。优先给引用（路径/链接/查询）而非全文。
5. **工具与返回要 token 高效**：工具集最小化且功能不重叠；工具返回结构化、可裁剪；子 agent 在隔离上下文探索重材料，只回 1k-2k token 的蒸馏摘要。

## 压缩与摘要（方法/风险）
- **Compaction（滚动摘要）**：临近上下文上限时，用 LLM 把旧会话压成摘要、新窗口重启。压缩时优先保：架构/关键决策、未解决的 bug、未完成事项、实现细节；丢弃冗余工具输出。压缩提示先调 recall（该留的别丢）再调 precision。
- **Agentic memory（结构化笔记）**：在上下文之外维护 NOTES.md / todo，需要时重载（Anthropic 的 Pokemon 示例跨数千步与多次重置仍能完成目标）。
- **子 agent 消化重上下文**：适合并行调研；compaction 适合来回对话；笔记适合里程碑式迭代。
- **服务器端 compaction / 上下文编辑**：Claude API 已原生支持服务端自动摘要与 context editing；Claude Code 会临近上限自动 compact 并保"代码模式、文件状态、关键决策"。
- **风险与缓解**：摘要必然有损——丢失细节、误引证；缓解：原始消息全量落库可溯源（记忆库/数据库），上下文只放"滚动摘要 + 最近窗口 + 检索到的高相关块"；可配置"compaction 时务必保留 XX"这类指令。

## Prompt Caching（机制/用法/成本）
- **机制**：KV cache，命中条件是**精确前缀匹配**（Anthropic 还支持 breakpoint 与逐块回退；缓存只在断点块写入、前缀哈希累计）。多轮对话天然契合：历史前缀逐轮累积、保持不变。
- **Anthropic 定价**：读 = 0.1x 基础输入价（省 90%）；写 = 1.25x（5m TTL）/ 2x（1h TTL）；默认 5m，可显式 1h；最小可缓存长度按模型 512~4096 token（多数 1024）；加断点不额外收费；缓存按 workspace 隔离；缓存 token 仍占上下文窗口（只省钱/省延迟，不省质量）。
- **OpenAI 定价**：gpt-4o 及更新自动开启（≥1024 token 才可缓存）；cached 输入价约原价 4-5 折；按前缀哈希路由（前 ~256 token）；静态内容（指令/示例/工具/大文档）放开头、可变内容（用户消息）放结尾。
- **用法**：system prompt + 工具定义 + 常驻文档 = 稳定前缀 → 每轮打 9 折/5 折且降 TTFT；断点放在"每次请求都相同的块"上（放时间戳/会话 id 之后必然 miss）；做 latency 敏感应用可预热（pre-warm）。

## 大上下文权衡（全量注入 vs 按需注入）
- 现状：Claude Sonnet 5 / Opus 系、GPT-4.1 等已默认 1M token 窗口，长文档"塞得下"。
- **不推荐"全塞"**：塞得下 ≠ 用得好——context rot + lost-in-the-middle 仍存在，token 越多召回越弱；成本线性上涨。官方建议"smallest set of high-signal tokens"。
- **推荐混合策略**：小量高价值常驻（CLAUDE.md 式，保证速度与稳定性）＋ 工具/检索/子 agent 按需取用（避免过期索引与冗余）。长文档需要精读时：结构化（XML 分节、表格化）、放首尾、或用子 agent 先提炼再问。
- 取舍结论：**对话式求职 agent 属"长会话 + 多文档"场景，应默认按需注入、只在大段精读（如改简历/深度匹配 JD）时全量注入单份文档，且放在当前轮末**（紧邻提问、避开上下文中间地带）。

## 对 job-helper 的上下文策略（P0/P1/P2）
- **P0 system prompt 分层结构**：XML 分节：`<role>` 求职助手角色 + `<rules>` 硬性规则（不伪造简历、不冒充求职者、脱敏） + `<workflow>` 流程定义（聊→建画像→改简历→搜岗→投递） + `<memory_schema>` 记忆库字段说明（对应 02 记忆专题的 memory_blocks）。稳定段放最前，兼顾缓存。
- **P0 简历/JD 不全文常驻**：首条注入"结构化简历概要（要点化）+ JD 匹配矩阵"（放对话开头，利用首尾位置优势）；**原文全文放记忆库/按工具返回**，需要逐字推敲时再注入到当前轮末尾。避免把两份长文并排堆在窗口中部。
- **P0 会话历史**：全量落库（SQLite messages 表，见 02 专题）；上下文只留最近 N 轮 + 当前任务状态；工具返回用后即清；临近上限触发 compaction（保：用户偏好、已投递进度、未决问题），跨会话靠 summary + memory_blocks 恢复，必要时"新会话 + 恢复提示"。
- **P0 记忆边界**：用户画像/偏好/简历字段 = 常驻 system prompt 块（工具读写）；当轮检索结果与文档 = 工具返回（用后即清）；低频历史事实 = 记忆库检索取回。
- **P1 prompt caching**：稳定前缀 = system prompt + 工具定义 + 简历常驻段（5m TTL），每轮对话与批量处理显著省成本；大段 JD/简历精读也放前缀后稳定位置，配合缓存命中。
- **P1 子 agent 隔离**：简历解析、JD 抽取、匹配分析交给子 agent，只回结构化摘要，主对话保持轻量。
- **P2 token 预算自监控**：利用模型的 context awareness（token_budget 系统提示）或自行统计，接近 70% 时主动提醒 compaction；渐进披露细化到"给 agent 文件路径，需要时用工具读指定章节"。
