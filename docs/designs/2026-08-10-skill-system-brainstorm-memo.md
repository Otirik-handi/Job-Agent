# job-helper skill 系统 · 讨论纪要（2026-08-10）

> 状态：**讨论中**，尚未到整理设计草案的地步。
> 本纪要只是讨论过程的锚点，随时可改、可推翻；与后续设计文档冲突时，以设计文档为准。

## 1. 背景与动机

- 项目功能链（简历分析 → 岗位导入 → 匹配 → 渠道发现 → 专属简历 → 投递 → 投递后状态 → 面试准备）已基本完善。
- 下一阶段目标：**单点强化质量**，主战场是 **LLM 输出**。
- 初始想法："使用 SKILL 强化 LLM 输出"——经过讨论，这实际指向一个更大的东西：**给 job-helper 装一个 skill 能力运行时**。

## 2. 根本问题：job-helper 算不算 agent

用户的质疑："job-helper 和 ZCode/Codex/Claude Code 比起来，结构太简单，完全不能算 agent，像是一个 LLM 调用器。"

讨论后的结论（一半对，一半不对）：

- **对的部分**：job-helper 的能力是**焊死的**。想让它多会一件事，就得改代码、发版。而通用 agent 的能力是**插拔的**——skill 是一套"说明书"（文字+规则），放进技能库，模型干活时就照着做。"能力焊死 vs 能力可插拔"是感觉差距的真正来源。
- **不对的部分**：job-helper 已有 agent 的骨架——手（11 个工具）、记忆（会话 + SQLite）、判断力（模型决策工具调用）、刹车（两段式审批）。这不是 LLM 调用器该有的东西。

## 3. 差距分析

| 要素 | job-helper | 通用 agent 运行时 |
|---|---|---|
| 模型决策 + 工具循环 | ✅ ToolLoopAgent | ✅ |
| 记忆 / 持久化 | ✅ 会话 + SQLite | ✅ |
| **能力可运行时加载** | ❌ 硬编码：加能力 = 写工具/提示词/schema/注册/前端卡片 | ✅ skill/plugin 系统，能力是**数据**，可动态加载、组合、由模型选择 |
| 环境交互（文件/命令/浏览器） | ⚠️ 只有读用户提供的本地文件路径 | ✅ 文件系统 + 沙箱 + 浏览器等 |
| 自我修正循环 | ⚠️ 只有机械重试（`【上次输出无效】请修正`），无语义自检 | ✅ 反思 / 规划 / 拆解子任务 / 子代理 |

真正缺的是第一行「能力可运行时加载」。其余差距（环境交互、自我修正）因定位而取舍。

## 4. 定位决定

- job-helper = **专精求职领域的 agent**，不是通用 agent。
- 因此舍去通用 agent 的能力：**不做**文件系统操作、命令执行、浏览器、子代理拆分等。理由：对求职场景无价值，反而带来复杂度、维护成本和风险。
- 钱和精力花在刀刃上：**让求职输出更准、更可信**。

## 5. skill 系统对 job-helper 的定义（大白话）

1. **把质量规则从代码里搬出来**：改进输出质量 = 写/改"说明书"文档，不用动代码。例：改进面试准备质量，不再是改 `prompts/interview-prep.ts`，而是写一份"面试准备输出规范"放进技能库，系统自动把它注入模型生成面试准备包时看的材料。
2. **说明书可分享、可下载**：别人写好的求职技巧 skill 装进来就能用，自沉淀的规则也可以给出去。
3. **模型"看得到"新能力**：装了什么 skill，模型干活时就能参考什么（现为写死的 11 个工具 + 固定提示词）。
